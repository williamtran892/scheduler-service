## Release scope and decisions

- **In this release:** `POST /appointments`, `GET /appointments/{id}` and the lifecycle transitions (reschedule, reassign, cancel, check-in, start, complete, no-show).
- **Not in this release:** public availability search, setup CRUD, the materialiser, rotas, holds, absences, capacity blocks, channel reservations, daily caps. Candidate bay and technician selection is an internal query inside booking.
- **Fixture, not materialiser.** Setup rows, customers, vehicles and FREE `time_slot` cells are loaded from `local/mysql/data.sql` at container start, with fixed ids so scenarios can name them. Cells are generated relative to `CURRENT_DATE` so the fixture never goes stale; scenarios express dates relatively.
- **Acceptance tests are black-box over HTTP.** Ledger state is asserted through the public appointment record, which carries the owned cell ranges, or through observable outcomes such as a second booking of the same slot. No test-only endpoints and no fake clock in the acceptance path. The one exception: scenarios that depend on the passage of time (no-show sweeper, late arrival) may use a direct database connection from the suite, only to backdate an appointment and its cells, then poll the public record.
- **Idempotency** is the natural booking key `(vehicle_id, customer_id, start_at, kind)` as a unique index, with the appointment insert first in the transaction (deviation D4). The appointment id is generated by the service and is the customer-facing reference.
