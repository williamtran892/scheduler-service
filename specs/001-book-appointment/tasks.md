# Tasks: Book an appointment

**Input**: Design documents from `/specs/001-book-appointment/`

**Prerequisites**: plan.md, spec.md, research.md, data-model.md, contracts/, quickstart.md

**Tests**: Required. The constitution mandates integration-first Gherkin (Principle I) and strict TDD with an approval gate (Principle II). Every test task comes before the code task it drives, and every task that writes unit tests is done only when the tests are **written, seen failing**.

**Organization**: Phases follow plan.md "Approach and order of work" (Behavior gate → schema and fixture → step definitions → unit tests → approval gate → code layer by layer → Green → Refactor → Docs → Review). The four user stories share one endpoint and one booking transaction, so a story cannot be shipped without the layers below it; instead each task carries the label of the stories it serves, and the traceability table at the end maps every story to its scenarios and tasks.

## Format: `[ID] [P?] [Story] Description`

- **[P]**: can run in parallel (different files, no dependency on an incomplete task)
- **[USn]**: user story from spec.md (US1 book and read back, US2 never double-booked, US3 safe to repeat, US4 clear refusals)

## Path Conventions

Single Go module at the repository root: `cmd/`, `internal/`, `local/mysql/`, `features/`, `test/acceptance/`, `docs/`.

## Implementation Strategy

There is no smaller shippable slice than the booking transaction itself, so the MVP is the whole of Phases 1 to 10 with US1 scenarios as the first to turn green; US2 to US4 scenarios turn green on the same code. Proving it: the Red gates (T012, T031) show every scenario and unit test failing for the right reason, the approval gate (T032) is passed, and the Green gate (T054 to T056) shows all of them passing.
